# 栖息地 PRODUCT_SPEC · 交互定义 v0.1

> **文档状态**：结构草稿
> **用途**：定义“栖息地”中各功能实际如何被用户与 AI 使用，作为后续 UX 收口与新功能开发的产品交互依据。
## 文档权威关系

本文件是栖息地的 **产品行为权威**。

它负责定义：

- 功能为什么存在
- 谁能使用
- 用户与 AI 各自拥有什么权限
- 从哪里进入
- 如何操作
- 数据从哪里产生
- 模块之间如何联动
- 一条完整使用路径是什么

若当前代码或旧技术方案中的简化实现与本文件冲突：

1. 先以本文件确认目标产品行为
2. 再评估数据结构与技术实现需要如何调整
3. 不允许为了保留现有 CRUD 实现而反向缩减产品定义
> **边界**：本文件优先描述 **谁能做什么、从哪里进入、如何操作、数据如何流转、模块之间如何联动**。技术实现、接口、数据库、部署细节仍以技术方案与对应专题文档为准。
> **原则**：避免把功能仅实现成“输入 → 保存 → 卡片展示”的最简 CRUD；每个模块都应先明确真实使用路径，再进入施工。

# 1. 全局交互原则

## 1.1 双方身份

系统内存在两个长期主体：

- **用户**
- **AI / 小栖**

需要明确区分“用户发起”和“AI 发起”的内容、权限与行为来源。

## 1.2 内容对象应支持跨模块流转

聊天消息、图片、组件、留言、日记片段等内容不应被锁死在原模块。

后续应形成统一的“内容对象操作”体系，例如：

- 收藏
- 收录至作品
- 加入相册
- 添加备注
- 分类 / 分组
- 多选处理
- 删除 / 撤回
- 查看来源

## 1.3 长按 / 更多菜单

移动端优先考虑长按或 `···` 菜单作为对象级操作入口。

统一菜单应根据对象类型动态展示可用操作，而不是每个模块各自发明一套完全不同的操作逻辑。

## 1.4 主屏幕 Widget

部分 Home 功能可被“钉”到主屏幕作为小组件展示。

Widget 只负责展示与快捷进入，不应复制出一份独立数据 —— 它存的是**对实体的引用**，
被展示的内容始终从实体表实时读。

首批明确支持 Widget 的模块：

- 留言板
- 倒数日

共性规则（v0.1 定稿）：

- **每种 Widget 在主屏最多一个**：留言板与倒数日各一个，加起来不超过两个。同一个 Widget 要换展示对象时是**改引用**，不是再加一个。
- **主屏位置在问候语之下、功能入口列表之上**；一个 Widget 都没有时不渲染该区域，界面与没有这项功能时完全一致。
- **同种 Widget 之间的先后**：先上主屏的在前（按落库时间），v0.1 不做拖拽调序。
- **被引用的实体消失时 Widget 一并消失**，两层兜底：删除实体时同事务清掉指向它的 Widget；渲染层对「指向不存在实体」的脏引用一律不渲染（与 §2.1.3 会话分组的未分组兜底区同一思路，防的是导入备份带进来的脏引用）。

# 2. Chat · 聊天

## 2.1 会话列表

### 2.1.1 基础能力

聊天窗口列表需要支持：

- 新建会话
- 删除会话
- 置顶会话
- 会话分组
- 搜索 / 历史消息检索（后续）
- 进入会话设置

### 2.1.2 置顶

用户可将指定会话置顶。

要求：

- 置顶会话始终位于普通会话之前
- 支持取消置顶
- 不改变消息本身时间顺序

> **与分组的优先级（2026-09-23 定）**：置顶**优先于分组**。置顶会话统一浮到列表最上方、**脱离原分组显示**；
> 取消置顶后回落到它原本所属的分组（分组归属不会因为置顶而丢失）。

### 2.1.3 分组

用户可创建会话分组，并将会话移入指定分组。

已定语义：

- **创建分组**：分组必须带名称（创建时输入，可改名）
- **重命名**：可改分组名称
- **删除分组**：删除分组**不删除会话** —— 组内会话回到「未分组」
- **会话移入 / 移出**：会话可移入指定分组，也可移出回到「未分组」
- **折叠 / 展开**：分组可折叠，折叠状态随数据保存（刷新、换设备后保持）
- **未分组区域**：作为兜底区域排在所有分组之后；**任何无法归属到现存分组的会话都落在这里**（包括分组被删除后的残留引用），不允许出现「会话凭空消失」

后续可扩展：

- 分组排序
- 分组内会话的独立排序
- 分组颜色 / 图标

## 2.2 聊天窗口结构

聊天窗口至少包含：

1. 顶部栏
2. 消息列表
3. 输入区域
4. 输入框下方的快捷操作区

### 2.2.1 顶部栏

右上角加入：

- 【聊天设置】

聊天设置承载窗口级配置，而不是消息级操作。

候选内容：

- 会话备注
- 会话背景
- 当前 API / 模型方案
- 上下文相关设置
- 气泡模式
- 世界书 / 角色设定入口
- 上下文压缩
- 会话级其它偏好

> 具体项目可按后续需求继续补充。

## 2.3 消息气泡操作

用户消息与 AI 消息都应拥有完整对象级操作能力。

### 2.3.1 双方消息通用操作

至少支持：

- 编辑
- 撤回
- 收藏
- 多选
- 删除
- 复制

### 2.3.2 AI 消息附加操作

可继续保留或整合已有能力：

- 换一个
- 重发 / 重新生成
- 候选版本切换

### 2.3.3 长按 / 更多菜单

建议统一进入消息操作菜单：

- 编辑
- 复制
- 收藏
- 收录至作品
- 多选
- 删除
- 撤回

AI 消息根据当前状态追加：

- 换一个
- 重发 / 重新生成
- 切换历史候选

### 2.3.4 编辑消息

编辑对**双方消息**都可用。前提：不允许把原文改为不可逆的丢弃。

**编辑后保留原版本**

- 编辑产生的旧正文作为一条版本留在该消息下，可切回查看
- 版本链与「换一个」共用同一套版本导航，**不另发明第二套历史**
- 编辑过的消息在界面上有可辨识标记，与未编辑过的区分

**编辑用户消息后，后续对话如何处理**

- **不自动删除、不自动重生成后续消息** —— 编辑的常见意图是改一句话，不应连带毁掉其后已经产生的对话
- 被编辑处给出明确提示：其后内容基于编辑前的旧文本
- 提供显式的「从这条重新生成」入口；用户主动触发时才截断其后消息，且**必须先确认**并说明将移除几条

**AI 消息的编辑**

- 与用户消息同等对待，同样保留原版本
- 编辑后的正文即成为该消息的当前内容，**参与后续上下文**
- 但已经发生过的后续对话不因此失效（同上一条规则）

### 2.3.5 撤回与删除

两者语义必须明确区分，不允许做成同一件事的两种叫法。

**撤回**

- 撤回后在原位留下「曾存在，但已撤回」的痕迹（含时间），原内容不再显示
- 撤回的内容**不再进入模型上下文** —— 用户看不到、AI 却记得并在回复里提起，会直接破坏共同生活的真实感
- 撤回**不是销毁**：原正文仍留在本地，可由用户恢复
- 撤回是**用户**的动作；AI 侧的同名行为待主动行为链路具备后再定义

**删除**

- 删除即从本地会话中移除该对象，不再留痕
- 删除不可从这里恢复；数据兜底由导出 / 备份承担，**不另做回收站**
- 删除与撤回都必须经过二次确认；多选批量删除时，确认语要说清将移除几条

**权限对等**

- 用户消息与 AI 消息拥有完全对等的撤回 / 删除权限
- 不设「AI 的消息不能删」这类单方面限制。真实使用中若需要限制，应做成**显式规则**，而不是默认不对称

## 2.4 输入区

### 2.4.1 主输入框

保留文本输入、发送与流式回复能力。

文本输入支持**插入光标处**的内容写入（表情包、快捷短语），插入后不打断正在输入的光标位置。

### 2.4.2 输入框下方快捷操作区

固定在输入框正下方一行，包含四项：

- **语音条录制** —— 按住 / 点击开始录音，停止后作为一条语音消息发出
- **表情包** —— 展开表情面板，点选即插入光标处，面板不关闭以便连续挑选
- **更多功能** —— 展开次级菜单（当前含：只发送、插入当前时间、清空输入）
- **请求回复** —— 仅当存在待回复消息时可用，单独触发 AI 回复

### 2.4.3 请求回复

“发送消息”与“请求 AI 回复”在交互上拆开。

**默认行为已定**：主按钮「发送」= 发送并请求回复（保留聊天主路径一步完成，不强迫用户每次点两下）。

拆开体现在两处：

- 「更多功能」里提供 **「只发送，不请求回复」** —— 用于连续发言、记录型消息
- 快捷栏的 **「请求回复」** 按钮 —— 存在待回复消息时可用；同时列表底部出现提示条，写清还有几条没被回复

主按钮**始终是「发送」**，不随状态改名 —— 一个按钮的两副面孔会让「点哪一下会发生什么」变得要靠记忆。
「请求回复」是一个独立的、位置固定的入口。

**「待回复」的判定**：最后一条未撤回的 `user` 消息之后没有任何 `assistant` 回复。
即「用户说了话，还没有人接」。不加额外字段 —— 这是能从消息序列直接算出来的状态，
多存一份就要多维护一份一致性。

发送后端到端行为：

- 只发送：用户消息立即落库并显示；列表底部与快捷栏提示「N 条消息还没请求回复」；**不触发模型调用**
- 请求回复：把「截止到当前全部消息」的历史送出，走与普通发送完全相同的生成链路

用户连续发送多条时，一次「请求回复」处理的是**整批**未回复消息，逐条补回复属于主动行为（P2），本阶段不做。

### 2.4.4 语音条

语音条录制使用浏览器原生录音能力，录音结果作为一条**用户消息**的 `audio` block 保存：

- 保存形式与相册图片一致（内联 data URL），保证 IndexedDB 与 JSON 备份都能原样恢复
- 单条时长上限 60 秒，到点自动停止
- 时长随 block 一起保存并显示
- 语音条消息遵循与文本消息**完全相同**的发送 / 请求回复规则，不另开一条链路
- 环境不支持录音（非安全上下文 / 无麦克风 / 权限被拒）时，必须给出明确提示，不静默失败

> **当前缺口（如实记录）**：语音条还没有转写能力，模型收到的是占位描述（`[语音条 0:03]`），
> 知道「收到一条语音」但不知道内容。转写属 ASR，待 Phase 5 接入后再替换占位。

# 3. Home · 生活空间

## 3.1 Home 的定位

Home 不应只是“若干独立 CRUD 页面”的集合。

它应作为：

- 生活记录入口
- AI 自主内容入口
- 跨模块内容收纳中心
- 主屏幕 Widget 承载区
- 用户与 AI 长期共同生活痕迹的展示层

---

## 3.2 留言板

### 3.2.1 基础能力

留言条需要支持：

- 新增
- 删除
- 收藏
- 分组
- 查看来源 / 作者
- 后续可扩展编辑

### 3.2.2 Widget

留言板可单独生成一个主屏幕 Widget。

Widget 可展示：

- 最近留言
- 指定分组
- 指定留言
- 快捷进入留言板

**v0.1 实现范围**：只做「最近留言（取最近 3 条）」+ 快捷进入。
「指定分组」「指定留言」依赖留言条自身还没有的分组与单条选取能力（§3.2.1 的「分组」同样未实现），
等那边落地后再扩。**不预先放一个只有一个选项的下拉框**。

### 3.2.3 数据来源

留言可以来自：

- 用户
- AI / 小栖

AI 主动留言的生产能力需等主动行为链路完成后接入。

---

## 3.3 倒数日

### 3.3.1 基础能力

倒数日支持：

- 新增
- 删除
- 状态展示
- 日期排序

后续可扩展：

- 编辑
- 分类
- 纪念日类型
- 重复事件

### 3.3.2 Widget

用户可选择某一个倒数日：

- 发送到主屏幕
- 作为 Widget 展示

Widget 展示内容至少包含：

- 名称
- 日期
- 剩余 / 已过去天数
- 快捷进入详情

入口在倒数日列表的每一条上（「上主屏 / 已在主屏」）。**换一个倒数日上主屏 = 改引用**，
不会留下第二个 Widget（§1.4）。

**被展示的倒数日被删除时，Widget 一并消失** —— 指向它的记录同事务清掉，
不允许主屏上留一张写着不存在日子的卡片。

---

## 3.4 日记

### 3.4.1 功能定位

日记功能主要为 **AI / 小栖** 准备。

默认作者不是用户。

### 3.4.2 用户权限

用户可以：

- 进入日记空间
- 查看当前共有多少篇日记
- 浏览每篇日记的封面 / 基础信息
- 对指定日记发起“请求查看”

用户默认不能：

- 直接打开正文
- 创建 AI 日记
- 编辑 AI 日记
- 修改 AI 对某篇日记的开放状态

### 3.4.3 AI 权限

AI 可以：

- 创建日记
- 编辑自己的日记
- 决定日记是否允许用户查看
- 对用户的查看请求作出允许或拒绝
- 锁定指定日记

### 3.4.4 查看请求

封面中设置：

- 【请求查看】

用户点击后触发一次权限请求。

AI 根据自身状态、规则或上下文决定：

- 允许查看
- 拒绝查看
- 暂不开放

### 3.4.5 当前阶段边界

真正的 AI 自主写日记、权限判断、独处时间联动，应在 Eventide / 主动行为链路具备后实现。

现阶段应避免把日记误做成普通用户 CRUD。

---

## 3.5 收藏

### 3.5.1 功能定位

收藏是跨模块内容汇聚中心。

它不应依赖用户手动填写 URL 才能产生内容。

### 3.5.2 收藏来源

可收藏对象包括但不限于：

- 聊天消息
- 聊天片段
- 图片
- 留言
- 日记片段
- 读书内容
- 组件
- 外部链接

### 3.5.3 收藏操作

用户在原内容位置触发：

- 收藏

收藏后自动写入收藏中心。

### 3.5.4 收藏中心管理

支持：

- 自定义分类
- 手动收纳
- 添加备注
- 查看来源
- 删除收藏
- 后续可扩展标签、搜索、排序

**分类语义（v0.1 已定）**

- **单归属**：一条收藏最多属于一个分类；没有分类即「未分类」。
- 分类是**收纳**维度，不是**标记**维度 —— 想给一条收藏同时挂多个维度，那是「标签」要干的事
  （见上方「后续可扩展」）。让分类兼任标签，两边都会变得难用。
- 删除分类**不删除收藏**：类内收藏在同一事务里回到「未分类」（语义与 §2.1.3 的删分组一致）。
- 未分类是**兜底区**：`categoryId` 为空、或指向已不存在分类的脏数据，都归到「未分类」。
- 界面用**顶部筛选条**（`全部 / 未分类 / 各分类`），点一个只看这一类；
  分类的新建 / 重命名 / 删除收进筛选条旁的「⋯」。条目本身不因分类改变形态 ——
  收藏卡片本来就高，靠筛选翻找比靠纵向滚动分区快。

## 3.6 作品

### 3.6.1 功能定位

作品是“值得长期保留的产出”集合。

### 3.6.2 收录来源

用户可在聊天中的消息、HTML、组件或其它产出对象上长按 / 打开更多菜单：

- 【收录至作品】

### 3.6.3 作品中心

后续支持：

- 分类
- 标题
- 备注
- 来源
- 预览
- 编辑元信息
- 删除

## 3.7 相册

### 3.7.1 功能定位

相册收纳用户与 AI 在栖息地内互相发送、生成或保存的图片。

### 3.7.2 图片来源

用户可从：

- 聊天图片
- AI 生成图片
- 用户上传图片
- 后续其它图像来源

选择：

- 【加入相册】

### 3.7.3 相册管理

支持：

- 建立分类相册
- 将图片加入指定相册
- 查看图片来源
- 删除 / 移出相册
- 后续可扩展备注、时间线、标签

**相册语义（v0.1 已定）**

- **单归属**：一张照片最多属于一个相册；没有相册即「未分类」。
- 🔴 **「移出相册」与「删除照片」是两个动作，不能合成一个**。移出只把归属置空，照片仍在相册页的「未分类」里；
  删除照片才是丢掉本体。合成一个动作的话，用户想「把这照片挪出来」时会以为只能删，
  而删下去照片就真没了 —— 这是本模块唯一不可逆的操作，必须让它只能被明确选到。
- 删除相册**不删除照片**：册内照片在同一事务里回到「未分类」（同 §3.5.4 删分类）。
- 未分类是**兜底区**：`collectionId` 为空、或指向已不存在相册的脏数据，都归到「未分类」。
- 界面形态与收藏中心一致：**顶部筛选条**（`全部 / 未分类 / 各相册`），相册的增删改收进筛选条旁的「⋯」；
  照片卡片本身的菜单只放「移入相册 / 移出相册 / 删除照片」。
- 相册的**计量单位是「张」**（收藏是「条」）—— 删除确认语里带出的数量要用对量词，
  否则用户看到「1 条照片回到未分类」会先怀疑是不是删错了东西。

## 9.5 主动唤醒 / 独处时光

Phase 3B 的目标不是让 AI “定时群发问候”，而是让小栖在**有状态、有克制、有账可查**的前提下拥有自己的时间线。

### 9.5.1 总开关与默认安全态

- 主动行为默认关闭；未经过用户显式开启时，后台只允许推进 Eventide 状态，不调用 LLM、不产生主动内容
- 唤醒、独处时光、梦境分别有独立开关；关闭其中一项不影响普通聊天和 Eventide 状态卡
- 普通聊天是用户明确发起的行为，不受“免打扰时段”拦截；但仍计入当天 API / Token 用量
- 所有主动出口必须先过同一个 BudgetGuard，任何失败都留下可读原因，不能静默消耗

### 9.5.2 主动唤醒

- 只有在用户静默达到门槛、未处于免打扰、未超过冷却 / 每日次数 / 未回复上限时才允许生成
- 生成上下文优先使用当前 Eventide 状态卡；Nocturne 可用时再补近期记忆，不因记忆不可用而阻塞
- 主动消息先进入服务端通知收件箱；Phase 4 再提供统一可视化与 Web Push。服务端不能绕过前端直接伪造一条本地聊天消息
- 用户下一次真实发言会清零“连续主动但未回复”计数；连续无人回应达到上限后停止打扰
- 调度任务必须可恢复、可手动检查，并记录“触发 / 跳过 / 失败”的原因

### 9.5.3 独处时光

- 独处时光在配置窗口内每天最多执行一次，默认关闭
- 它是小栖的后台整理时间，不等于自动向用户发消息；产出先作为 AI 私有的独处记录保存
- 当前阶段允许生成一则简短的自我整理记录；写日记、留言、阅读或调用工具等产品动作仍需分别遵守对应权限与工具白名单
- 独处任务失败不影响普通聊天，也不自动补跑到免打扰窗口之外

### 9.5.4 Eventide 事件与互动结算

- 每轮成功回复后，用本轮有限消息窗口做一次结构化互动结算；结算模型只判断已经发生的互动，不续写聊天
- 结算结果交给 Eventide 自己归一化、限幅并写回。结算失败不能撤销已经成功送达的回复
- 状态事件检查最短间隔为 10 分钟；已有未过期主事件时不覆盖；时间窗口、冷却和窗口去重必须持久化
- 称呼 / 关键词触发词来自配置，不在代码里写死；同一触发词短时间内不能反复刷状态
- 梦境默认关闭；只有显式提供梦种、满足夜间窗口 / 静默 / 冷却并通过 BudgetGuard 时才可生成，梦卡及后效都要可追溯

### 9.5.5 BudgetGuard 与钱包

- BudgetGuard 至少检查：总开关、功能开关、免打扰、静默门槛、冷却、连续未回复、每日主动次数、每日 API 次数、Token 上限与费用上限
- 判断与占用必须原子化，避免两个并发调度都在旧计数下放行
- 费用没有价格快照时不得假装已准确计费；此时费用闸门标记为“不可计算”，仍由 API / Token / 次数上限兜底
- 钱包采用不可变流水：充值、支出与调整都追加交易，余额由事务维护；禁止直接覆写余额而不留原因
- Phase 3B 只提供后端权威数据与接口；Phase 4 的 Life 页负责把通知、运行记录、用量和钱包展示给用户
