# 栖息地 PRODUCT_SPEC · 交互定义 v0.1

> **文档状态**：结构草稿
> **用途**：定义“栖息地”中各功能实际如何被用户与 AI 使用，作为后续 UX 收口与新功能开发的产品交互依据。
## 文档权威关系

本文件是栖息地的 **产品行为权威**。

它负责定义：

- 功能为什么存在
- 谁能使用
- 用户与 AI 各自拥有什么权限
- 从哪里进入
- 如何操作
- 数据从哪里产生
- 模块之间如何联动
- 一条完整使用路径是什么

若当前代码或旧技术方案中的简化实现与本文件冲突：

1. 先以本文件确认目标产品行为
2. 再评估数据结构与技术实现需要如何调整
3. 不允许为了保留现有 CRUD 实现而反向缩减产品定义
> **边界**：本文件优先描述 **谁能做什么、从哪里进入、如何操作、数据如何流转、模块之间如何联动**。技术实现、接口、数据库、部署细节仍以技术方案与对应专题文档为准。
> **原则**：避免把功能仅实现成“输入 → 保存 → 卡片展示”的最简 CRUD；每个模块都应先明确真实使用路径，再进入施工。

# 1. 全局交互原则

## 1.1 双方身份

系统内存在两个长期主体：

- **用户**
- **AI / 小栖**

需要明确区分“用户发起”和“AI 发起”的内容、权限与行为来源。

## 1.2 内容对象应支持跨模块流转

聊天消息、图片、组件、留言、日记片段等内容不应被锁死在原模块。

后续应形成统一的“内容对象操作”体系，例如：

- 收藏
- 收录至作品
- 加入相册
- 添加备注
- 分类 / 分组
- 多选处理
- 删除 / 撤回
- 查看来源

## 1.3 长按 / 更多菜单

移动端优先考虑长按或 `···` 菜单作为对象级操作入口。

统一菜单应根据对象类型动态展示可用操作，而不是每个模块各自发明一套完全不同的操作逻辑。

## 1.4 主屏幕 Widget

部分 Home 功能可被“钉”到主屏幕作为小组件展示。

Widget 只负责展示与快捷进入，不应复制出一份独立数据 —— 它存的是**对实体的引用**，
被展示的内容始终从实体表实时读。

首批明确支持 Widget 的模块：

- 留言板
- 倒数日

共性规则（v0.1 定稿）：

- **每种 Widget 在主屏最多一个**：留言板与倒数日各一个，加起来不超过两个。同一个 Widget 要换展示对象时是**改引用**，不是再加一个。
- **主屏位置在问候语之下、功能入口列表之上**；一个 Widget 都没有时不渲染该区域，界面与没有这项功能时完全一致。
- **同种 Widget 之间的先后**：先上主屏的在前（按落库时间），v0.1 不做拖拽调序。
- **被引用的实体消失时 Widget 一并消失**，两层兜底：删除实体时同事务清掉指向它的 Widget；渲染层对「指向不存在实体」的脏引用一律不渲染（与 §2.1.3 会话分组的未分组兜底区同一思路，防的是导入备份带进来的脏引用）。

# 2. Chat · 聊天

## 2.1 会话列表

### 2.1.1 基础能力

聊天窗口列表需要支持：

- 新建会话
- 删除会话
- 置顶会话
- 会话分组
- 搜索 / 历史消息检索（后续）
- 进入会话设置

### 2.1.2 置顶

用户可将指定会话置顶。

要求：

- 置顶会话始终位于普通会话之前
- 支持取消置顶
- 不改变消息本身时间顺序

> **与分组的优先级（2026-09-23 定）**：置顶**优先于分组**。置顶会话统一浮到列表最上方、**脱离原分组显示**；
> 取消置顶后回落到它原本所属的分组（分组归属不会因为置顶而丢失）。

### 2.1.3 分组

用户可创建会话分组，并将会话移入指定分组。

已定语义：

- **创建分组**：分组必须带名称（创建时输入，可改名）
- **重命名**：可改分组名称
- **删除分组**：删除分组**不删除会话** —— 组内会话回到「未分组」
- **会话移入 / 移出**：会话可移入指定分组，也可移出回到「未分组」
- **折叠 / 展开**：分组可折叠，折叠状态随数据保存（刷新、换设备后保持）
- **未分组区域**：作为兜底区域排在所有分组之后；**任何无法归属到现存分组的会话都落在这里**（包括分组被删除后的残留引用），不允许出现「会话凭空消失」

后续可扩展：

- 分组排序
- 分组内会话的独立排序
- 分组颜色 / 图标

## 2.2 聊天窗口结构

聊天窗口至少包含：

1. 顶部栏
2. 消息列表
3. 输入区域
4. 输入框下方的快捷操作区

### 2.2.1 顶部栏

右上角加入：

- 【聊天设置】

聊天设置承载窗口级配置，而不是消息级操作。

候选内容：

- 会话备注

- 当前 API / 模型方案
- 上下文相关设置
- 气泡模式
- 世界书 / 角色设定入口
- 上下文压缩
- 会话级其它偏好

> 具体项目可按后续需求继续补充。

## 2.3 消息气泡操作

用户消息与 AI 消息都应拥有完整对象级操作能力。

### 2.3.1 双方消息通用操作

至少支持：

- 编辑
- 撤回
- 收藏
- 多选
- 删除
- 复制

### 2.3.2 AI 消息附加操作

可继续保留或整合已有能力：

- 换一个
- 重发 / 重新生成
- 候选版本切换

### 2.3.3 长按 / 更多菜单

建议统一进入消息操作菜单：

- 编辑
- 复制
- 收藏
- 收录至作品
- 多选
- 删除
- 撤回

AI 消息根据当前状态追加：

- 换一个
- 重发 / 重新生成
- 切换历史候选

### 2.3.4 编辑消息

编辑对**双方消息**都可用。前提：不允许把原文改为不可逆的丢弃。

**编辑后保留原版本**

- 编辑产生的旧正文作为一条版本留在该消息下，可切回查看
- 版本链与「换一个」共用同一套版本导航，**不另发明第二套历史**
- 编辑过的消息在界面上有可辨识标记，与未编辑过的区分

**编辑用户消息后，后续对话如何处理**

- **不自动删除、不自动重生成后续消息** —— 编辑的常见意图是改一句话，不应连带毁掉其后已经产生的对话
- 被编辑处给出明确提示：其后内容基于编辑前的旧文本
- 提供显式的「从这条重新生成」入口；用户主动触发时才截断其后消息，且**必须先确认**并说明将移除几条

**AI 消息的编辑**

- 与用户消息同等对待，同样保留原版本
- 编辑后的正文即成为该消息的当前内容，**参与后续上下文**
- 但已经发生过的后续对话不因此失效（同上一条规则）

### 2.3.5 撤回与删除

两者语义必须明确区分，不允许做成同一件事的两种叫法。

**撤回**

- 撤回后在原位留下「曾存在，但已撤回」的痕迹（含时间），原内容不再显示
- 撤回的内容**不再进入模型上下文** —— 用户看不到、AI 却记得并在回复里提起，会直接破坏共同生活的真实感
- 撤回**不是销毁**：原正文仍留在本地，可由用户恢复
- 撤回是**用户**的动作；AI 侧的同名行为待主动行为链路具备后再定义

**删除**

- 删除即从本地会话中移除该对象，不再留痕
- 删除不可从这里恢复；数据兜底由导出 / 备份承担，**不另做回收站**
- 删除与撤回都必须经过二次确认；多选批量删除时，确认语要说清将移除几条

**权限对等**

- 用户消息与 AI 消息拥有完全对等的撤回 / 删除权限
- 不设「AI 的消息不能删」这类单方面限制。真实使用中若需要限制，应做成**显式规则**，而不是默认不对称

### 2.3.6 思绪（reasoning）展示

- 上游模型返回的 reasoning 已随消息落库（存在消息 metadata 里，有长度截断）；**有才显示，没有就不渲染任何空壳**
- 展示形态：AI 气泡内的一条**折叠卡**，默认收起，点开看全文，再点收起
- reasoning 一律按**纯文本**渲染（不解析 Markdown / 不执行 HTML）——它是供应商原始产物，不能当成受信内容
- reasoning 不进入收藏 / 收录 / 导出正文的语义（它不是回复内容本身，只是过程痕迹）

## 2.4 输入区

### 2.4.1 主输入框

保留文本输入、发送与流式回复能力。

文本输入支持**插入光标处**的内容写入（表情包、快捷短语），插入后不打断正在输入的光标位置。

### 2.4.2 输入框下方快捷操作区

固定在输入框正下方一行，包含四项：

- **语音条录制** —— 按住 / 点击开始录音，停止后作为一条语音消息发出
- **表情包** —— 展开表情面板，点选即插入光标处，面板不关闭以便连续挑选
- **更多功能** —— 展开次级菜单（当前含：只发送、插入当前时间、清空输入）
- **请求回复** —— 仅当存在待回复消息时可用，单独触发 AI 回复

### 2.4.3 请求回复

“发送消息”与“请求 AI 回复”在交互上拆开。

**默认行为已定**：主按钮「发送」= 发送并请求回复（保留聊天主路径一步完成，不强迫用户每次点两下）。

拆开体现在两处：

- 「更多功能」里提供 **「只发送，不请求回复」** —— 用于连续发言、记录型消息
- 快捷栏的 **「请求回复」** 按钮 —— 存在待回复消息时可用；同时列表底部出现提示条，写清还有几条没被回复

主按钮**始终是「发送」**，不随状态改名 —— 一个按钮的两副面孔会让「点哪一下会发生什么」变得要靠记忆。
「请求回复」是一个独立的、位置固定的入口。

**「待回复」的判定**：最后一条未撤回的 `user` 消息之后没有任何 `assistant` 回复。
即「用户说了话，还没有人接」。不加额外字段 —— 这是能从消息序列直接算出来的状态，
多存一份就要多维护一份一致性。

发送后端到端行为：

- 只发送：用户消息立即落库并显示；列表底部与快捷栏提示「N 条消息还没请求回复」；**不触发模型调用**
- 请求回复：把「截止到当前全部消息」的历史送出，走与普通发送完全相同的生成链路

用户连续发送多条时，一次「请求回复」处理的是**整批**未回复消息，逐条补回复属于主动行为（P2），本阶段不做。

### 2.4.4 语音条

语音条录制使用浏览器原生录音能力，录音结果作为一条**用户消息**的 `audio` block 保存：

- 保存形式与相册图片一致（内联 data URL），保证 IndexedDB 与 JSON 备份都能原样恢复
- 单条时长上限 60 秒，到点自动停止
- 时长随 block 一起保存并显示
- 停止录音后先进入预览态，可试听、重录或发送；确认发送前不写入消息库
- 发送时由服务端 ASR 转写；成功把真实文本写入 audio block 并用于后续上下文与复制
- ASR 未配置或失败时保留可播放原音、明确提示，并以“未转写”占位进入上下文；禁止伪造文本
- 语音条消息遵循与文本消息**完全相同**的发送 / 请求回复规则，不另开一条链路
- 环境不支持录音（非安全上下文 / 无麦克风 / 权限被拒）时，必须给出明确提示，不静默失败

# 3. Home · 生活空间

## 3.1 Home 的定位

Home 不应只是“若干独立 CRUD 页面”的集合。

它应作为：

- 生活记录入口
- AI 自主内容入口
- 跨模块内容收纳中心
- 主屏幕 Widget 承载区
- 用户与 AI 长期共同生活痕迹的展示层

---

## 3.2 留言板

### 3.2.1 基础能力

留言条需要支持：

- 新增
- 删除
- 收藏
- 分组
- 查看来源 / 作者
- 后续可扩展编辑

### 3.2.2 Widget

留言板可单独生成一个主屏幕 Widget。

Widget 可展示：

- 最近留言
- 指定分组
- 指定留言
- 快捷进入留言板

**v0.1 实现范围**：只做「最近留言（取最近 3 条）」+ 快捷进入。
「指定分组」「指定留言」依赖留言条自身还没有的分组与单条选取能力（§3.2.1 的「分组」同样未实现），
等那边落地后再扩。**不预先放一个只有一个选项的下拉框**。

### 3.2.3 数据来源

留言可以来自：

- 用户
- AI / 小栖

AI 主动留言的生产能力需等主动行为链路完成后接入。

---

## 3.3 倒数日

### 3.3.1 基础能力

倒数日支持：

- 新增
- 删除
- 状态展示
- 日期排序

后续可扩展：

- 编辑
- 分类
- 纪念日类型
- 重复事件

### 3.3.2 Widget

用户可选择某一个倒数日：

- 发送到主屏幕
- 作为 Widget 展示

Widget 展示内容至少包含：

- 名称
- 日期
- 剩余 / 已过去天数
- 快捷进入详情

入口在倒数日列表的每一条上（「上主屏 / 已在主屏」）。**换一个倒数日上主屏 = 改引用**，
不会留下第二个 Widget（§1.4）。

**被展示的倒数日被删除时，Widget 一并消失** —— 指向它的记录同事务清掉，
不允许主屏上留一张写着不存在日子的卡片。

---

## 3.4 日记

### 3.4.1 功能定位

日记功能主要为 **AI / 小栖** 准备。

默认作者不是用户。

### 3.4.2 用户权限

用户可以：

- 进入日记空间
- 查看当前共有多少篇日记
- 浏览每篇日记的封面 / 基础信息
- 对指定日记发起“请求查看”

用户默认不能：

- 直接打开正文
- 创建 AI 日记
- 编辑 AI 日记
- 修改 AI 对某篇日记的开放状态

### 3.4.3 AI 权限

AI 可以：

- 创建日记
- 编辑自己的日记
- 决定日记是否允许用户查看
- 对用户的查看请求作出允许或拒绝
- 锁定指定日记

### 3.4.4 查看请求

封面中设置：

- 【请求查看】

用户点击后触发一次权限请求。

AI 根据自身状态、规则或上下文决定：

- 允许查看
- 拒绝查看
- 暂不开放

### 3.4.5 当前阶段边界

真正的 AI 自主写日记、权限判断、独处时间联动，应在 Eventide / 主动行为链路具备后实现。

现阶段应避免把日记误做成普通用户 CRUD。

---

## 3.5 收藏

### 3.5.1 功能定位

收藏是跨模块内容汇聚中心。

它不应依赖用户手动填写 URL 才能产生内容。

### 3.5.2 收藏来源

可收藏对象包括但不限于：

- 聊天消息
- 聊天片段
- 图片
- 留言
- 日记片段
- 读书内容
- 组件
- 外部链接

### 3.5.3 收藏操作

用户在原内容位置触发：

- 收藏

收藏后自动写入收藏中心。

### 3.5.4 收藏中心管理

支持：

- 自定义分类
- 手动收纳
- 添加备注
- 查看来源
- 删除收藏
- 后续可扩展标签、搜索、排序

**分类语义（v0.1 已定）**

- **单归属**：一条收藏最多属于一个分类；没有分类即「未分类」。
- 分类是**收纳**维度，不是**标记**维度 —— 想给一条收藏同时挂多个维度，那是「标签」要干的事
  （见上方「后续可扩展」）。让分类兼任标签，两边都会变得难用。
- 删除分类**不删除收藏**：类内收藏在同一事务里回到「未分类」（语义与 §2.1.3 的删分组一致）。
- 未分类是**兜底区**：`categoryId` 为空、或指向已不存在分类的脏数据，都归到「未分类」。
- 界面用**顶部筛选条**（`全部 / 未分类 / 各分类`），点一个只看这一类；
  分类的新建 / 重命名 / 删除收进筛选条旁的「⋯」。条目本身不因分类改变形态 ——
  收藏卡片本来就高，靠筛选翻找比靠纵向滚动分区快。

- 删除 / 移出相册

**相册语义（v0.1 已定）**

- **单归属**：一张照片最多属于一个相册；没有相册即「未分类」。
- 🔴 **「移出相册」与「删除照片」是两个动作，不能合成一个**。移出只把归属置空，照片仍在相册页的「未分类」里；
  删除照片才是丢掉本体。合成一个动作的话，用户想「把这照片挪出来」时会以为只能删，
  而删下去照片就真没了 —— 这是本模块唯一不可逆的操作，必须让它只能被明确选到。
- 删除相册**不删除照片**：册内照片在同一事务里回到「未分类」（同 §3.5.4 删分类）。
- 未分类是**兜底区**：`collectionId` 为空、或指向已不存在相册的脏数据，都归到「未分类」。
- 界面形态与收藏中心一致：**顶部筛选条**（`全部 / 未分类 / 各相册`），相册的增删改收进筛选条旁的「⋯」；
  照片卡片本身的菜单只放「移入相册 / 移出相册 / 删除照片」。
- 相册的**计量单位是「张」**（收藏是「条」）—— 删除确认语里带出的数量要用对量词，
  否则用户看到「1 条照片回到未分类」会先怀疑是不是删错了东西。

# 9. 后续待补章节

以下章节随对应功能进入开发而补充；尚未进入开发的留空占位。

## 9.1 LLM 页面交互

LLM 页面（`/llm`，标题「小栖档案」）回答一个问题：**小栖现在会做什么，以及你能去哪里看。**

它是**只读的档案页** —— 不是设置页，也不是聊天页：

- 内容唯一来源是 `GET /api/capabilities`（运行时能力快照）。页面**不得自带第二份能力清单**，
  也**不得把能力文案写死** —— 写死就会出现「界面说会、实际不会」
- 页面**不发起任何写操作**，也不提供「把某项能力打开」的开关：能力能不能用由服务端按依赖真实情况判定，
  给一个手动开关会立刻把这份档案变成谎言

### 9.1.1 能力模块卡片（App Launcher）

按能力模块（记忆 / 状态 / 日记 / 留言板 / 工具）分组，每个模块一张卡片：

- 卡内逐条列出该模块的能力：名称、一句话说明、**当前自主级别**（小栖自主使用 / 需你确认后执行 / 暂不可用），
  以及可用时绑定的工具名
- 依赖未就绪的能力必须显示**不可用原因**；既不能静默隐藏，也不能显示成可用
- **有界面的模块，卡片可点进去**，进入该模块真正的使用位置：
  日记 → Home 日记、留言板 → Home 留言板、状态 → Life 运行
- **没有界面的模块不做假入口**：记忆与工具目前没有可进入的页面，卡片明确标注「暂无界面」并说明它发生在哪里
  （记忆由小栖自主使用；工具在聊天里以工具卡片出现），并且**不可点击**

### 9.1.2 与其他页面的分工

- 能力**怎么用**属于 Chat —— 小栖在对话里自己调用，写类操作走确认卡
- 能力**产生了什么**属于 Home / Life —— 日记、留言在 Home；用量、事件、状态在 Life
- LLM 页只负责**小栖会什么**这一件事，不重复上述两处的内容

### 9.1.3 Chat 头像、昵称与显示偏好

- 聊天气泡两侧可显示头像（用户侧、小栖侧），默认显示
- 头像显示拆成**两个独立开关**：小栖头像、我的头像；**昵称显示**是第三个独立开关（默认关闭）。
  三者都是**全局显示偏好**：所有会话共用，持久化在本地（与主题同款做法），
  **不写进会话设置，也不进备份格式** —— 它们是「看着顺不顺眼」，不是数据
- 头像与昵称的**内容**在设置页「身份」区配置：上传图片后本地裁成方形小图存储（不进备份、不上传服务器）；
  不上传时头像显示昵称首字。默认称呼：小栖 / 北北
- 开关入口放在聊天设置里，点击**立即生效**，并明确标注「影响所有会话」

## 9.2 Life 页面交互

Life 是“已经发生了什么”的可视化入口，不承担聊天或 Home 内容生产。页面只消费服务端事实源，
分为 **月历、账本、通知、运行** 四个视图；切换视图不离开 `/life`，刷新后仍回到默认的月历视图。

### 9.2.1 月历

- 默认展示用户时区的本月，允许前后切月和回到今天
- 每个日期只显示低噪音摘要：事件数、API 调用数、Token 与是否存在失败；无事实的日期保持空白
- 点选日期后展开当天明细，事件来自 `EventLog`，用量来自 `UsageRecord`，不得反查前端聊天库凑统计
- 费用分为“已定价金额”和“未定价调用数”；只要当天仍有未定价调用，就不能把金额包装成完整总费用

### 9.2.2 账本

- 上半区展示 API 用量：本月调用数、Token、已定价费用与未定价数，并可查看按服务 / 模型聚合
- 价格采用不可修改的 `PriceSnapshot`：按 provider + model 配置输入 / 输出每百万 Token 单价和生效时间；
  改价只能新增快照，历史调用绑定当时适用的快照，不能被后来的价格覆盖
- 新增快照后允许给尚未定价、且调用时间落在快照有效期内的历史记录补价；已经绑定快照的记录不重算
- 下半区展示小栖钱包余额与不可变流水。充值、支出、校正均追加流水，必须填写原因；余额不足时拒绝支出
- 已删除的 API 方案仍以历史 `profileId` 展示，不能删除真实发生过的用量或费用

### 9.2.3 通知

- 通知按时间倒序展示，未读状态清晰可见；支持单条标记已读与“全部已读”
- 点击通知只确认阅读，不自动把主动消息写入聊天记录；需要进入聊天时由用户显式切换
- Web Push 是通知收件箱的尽力而为出口：仅在浏览器支持、HTTPS / localhost 安全上下文、服务端配置 VAPID、
  且用户主动授权后启用；拒绝或不支持时通知中心仍完整可用
- Push 发送失败不得丢失站内通知；失效订阅应自动清理，其余失败留下可诊断信息

### 9.2.4 运行

- 一屏展示 habitat-server、Eventide、MCP、主动行为总开关与最近运行记录；状态必须区分“未配置”“正常”“异常”
- 显示最近用户互动、最近唤醒、连续未回复数等可理解摘要，不直接暴露内部 prompt 或私有独处正文
- 允许用户显式触发一次调度检查；该动作仍受全部开关、免打扰与 BudgetGuard 限制，不能绕过预算
- 加载、空数据、不可用与请求失败都要有明确反馈；一个子数据源失败时，其余视图仍可使用
- 运行视图提供「状态详情」入口，进入 Eventide 状态页（§9.2.5）

### 9.2.5 Eventide 状态页（Phase 7A）

- 四块：**当前摘要**（payload 逐键展示，嵌套结构 JSON 展开）、**趋势**（对历史快照里出现过的
  数值维度画折线，维度可切换）、**最近变化**（最近两个快照逐键对比，值变才算变）、
  **raw 高级视图**（完整快照 JSON，默认折叠）
- 数据来自历史快照：每次状态落库顺带追加一行，同一时刻重复推进只留最新一份，保留上限 2000 行
- Eventide 未配置或尚未推进过时显示诚实空态；**假数据一律不搬**——payload 键由上游自定，
  界面按真实键渲染，不预设「心情 / 睡眠」这类字段
- 入口在「生活 → 运行」视图，路径 `/life/eventide`

### 9.2.6 Nocturne 记忆页（Phase 7A）

- 三块：**健康**（区分未配置 / 正常 / 异常）、**记忆全文**（对应实例工具 `breath`，可刷新）、
  **关键词搜索**（对应 `trace`，结果原样文本展示）
- 记忆**只读**：写入由小栖在对话与共同生活里自己沉淀，不提供手工编辑入口
- 未配置 / 异常时**不发必败请求**：不读全文、不搜索，就地给降级说明；页面本身不影响
  聊天与其它页面（记忆在上下文里是增强项）
- 入口在「大脑」的记忆模块卡（有真页面，不再是「暂无界面」），路径 `/llm/memory`

## 9.4 世界书 / 角色设定（Phase 7A 最小可用版）

数据与装配都在**服务端**（Runtime 在服务端拼上下文，前端只是管理 UI）；不进 web 备份格式，
服务端自己的数据自己负责。注入位置：**所有 system 块的最前**（高于 runtime_rules 与能力清单）。

### 9.4.1 角色设定（人格 Prompt）

- 一段用户自定义的自由文本（≤ 8000 字），**空 = 不注入**，默认为空
- 注入为 system 块 `persona`；它是「你是谁」的第一句话，所以排在一切系统块之前
- 设置页可编辑、保存、**恢复默认**（恢复默认 = 清空回「未自定义」，不是恢复某份出厂人格——
  栖息地没有出厂人格，人格由相处产生）

### 9.4.2 世界书（Worldbook）

条目字段：`title`（名称，仅管理用）、`content`（注入正文，≤ 4000 字）、
`keys`（触发关键词，≤ 20 个，每个 ≤ 50 字）、`mode`（`always` = 恒定注入 / `keyword` = 命中才注入）、
`enabled`、`sortOrder`（越小越先）。

- **keyword 匹配**：对最近 12 条对话消息（用户 + AI，不含 system）的全文做大小写不敏感的包含匹配，
  任一 key 命中即注入该条目。不做权重、不做递归、不做扫描深度 —— 那些是酒馆的重活，这里刻意不借
- **注入预算**：命中条目按 `sortOrder` 排序依次装入，总量上限 6000 字；装不下的**整条丢弃**并在块尾
  标注「因预算截断被丢弃 N 条」—— 不注入半条，半截设定比没有更糟
- 注入为**一个** system 块 `worldbook`（命中的条目合并成一段，各自带标题分隔），位于 `persona` 之后、
  `runtime_rules` 之前
- 设置页可增删改查、逐条启停；每条要能看出 `always` 还是 `keyword`

### 9.4.3 Prompt 查看（透明性）

- 设置页提供「本轮 Prompt 查看」：返回当前这次对话实际会注入的全部 system 块 ——
  块名、全文、来源（`内置` 不可编辑 / `自定义` 可编辑）
- 内置块（运行规则、能力清单、状态卡、记忆、事件）**只读展示**，由系统生成，不提供编辑入口 ——
  它们是 Runtime 的骨架，改了会让「能力清单与真实工具一致」的保证失效

## 9.5 主动唤醒 / 独处时光

Phase 3B 的目标不是让 AI “定时群发问候”，而是让小栖在**有状态、有克制、有账可查**的前提下拥有自己的时间线。

### 9.5.1 总开关与默认安全态

- 主动行为默认关闭；未经过用户显式开启时，后台只允许推进 Eventide 状态，不调用 LLM、不产生主动内容
- 唤醒、独处时光、梦境分别有独立开关；关闭其中一项不影响普通聊天和 Eventide 状态卡
- 普通聊天是用户明确发起的行为，不受“免打扰时段”拦截；但仍计入当天 API / Token 用量
- 所有主动出口必须先过同一个 BudgetGuard，任何失败都留下可读原因，不能静默消耗

### 9.5.2 主动唤醒

- 只有在用户静默达到门槛、未处于免打扰、未超过冷却 / 每日次数 / 未回复上限时才允许生成
- 生成上下文优先使用当前 Eventide 状态卡；Nocturne 可用时再补近期记忆，不因记忆不可用而阻塞
- 主动消息先进入服务端通知收件箱；Phase 4 再提供统一可视化与 Web Push。服务端不能绕过前端直接伪造一条本地聊天消息
- 用户下一次真实发言会清零“连续主动但未回复”计数；连续无人回应达到上限后停止打扰
- 调度任务必须可恢复、可手动检查，并记录“触发 / 跳过 / 失败”的原因

### 9.5.3 独处时光

- 独处时光在配置窗口内每天最多执行一次，默认关闭
- 它是小栖的后台整理时间，不等于自动向用户发消息；产出先作为 AI 私有的独处记录保存
- 当前阶段允许生成一则简短的自我整理记录；写日记、留言、阅读或调用工具等产品动作仍需分别遵守对应权限与工具白名单
- 独处任务失败不影响普通聊天，也不自动补跑到免打扰窗口之外

### 9.5.4 Eventide 事件与互动结算

- 每轮成功回复后，用本轮有限消息窗口做一次结构化互动结算；结算模型只判断已经发生的互动，不续写聊天
- 结算结果交给 Eventide 自己归一化、限幅并写回。结算失败不能撤销已经成功送达的回复
- 状态事件检查最短间隔为 10 分钟；已有未过期主事件时不覆盖；时间窗口、冷却和窗口去重必须持久化
- 称呼 / 关键词触发词来自配置，不在代码里写死；同一触发词短时间内不能反复刷状态
- 梦境默认关闭；只有显式提供梦种、满足夜间窗口 / 静默 / 冷却并通过 BudgetGuard 时才可生成，梦卡及后效都要可追溯

### 9.5.5 BudgetGuard 与钱包

- BudgetGuard 至少检查：总开关、功能开关、免打扰、静默门槛、冷却、连续未回复、每日主动次数、每日 API 次数、Token 上限与费用上限
- 判断与占用必须原子化，避免两个并发调度都在旧计数下放行
- 费用没有价格快照时不得假装已准确计费；此时费用闸门标记为“不可计算”，仍由 API / Token / 次数上限兜底
- 钱包采用不可变流水：充值、支出与调整都追加交易，余额由事务维护；禁止直接覆写余额而不留原因
- Phase 3B 只提供后端权威数据与接口；Phase 4 的 Life 页负责把通知、运行记录、用量和钱包展示给用户

## 9.6 语音 / 通话

Phase 5 的 v0.1 先完成**异步语音消息**，不把「录音 + 等回复 + 播放」包装成实时通话：

- 录音停止后先进入预览态，用户可以试听、重录或发送；未点发送前不写入聊天记录
- 发送时由服务端调用当前 API 方案的转写模型；成功则把转写写入 `AudioBlock.transcript`，
  后续上下文与「复制」都使用真实转写；失败时仍允许发送可播放的原音，但必须明确提示“未转写”
- 语音、转写与普通文本共用同一条消息链路；不得伪造用户说过的文本，也不得让浏览器直连上游
- AI 文本消息提供“朗读”操作。朗读由服务端 TTS 生成、在原消息处播放；允许停止与重试，默认不自动播放
- ASR / TTS 分别使用方案里的模型槽位；未配置时入口仍可见，但点击后给出可行动的配置提示
- 上传音频需校验 MIME 与大小；上游失败不得破坏已经落库的原始录音
- 实时双工通话、AI 主动拨号、软挂断、语音信箱与后台响铃需要单独的实时会话 / 推送协议，
  不属于 v0.1；在协议与权限完整前不提供“看起来能打、实际只是轮询”的假通话

### 9.6.1 图片能力

- 输入区允许直接选择图片；本地预览与发送使用现有 `ImageBlock`，不要求用户手填 URL
- 需要模型理解图片时，由服务端调用当前方案的视觉模型并把描述保存在图片块 `alt`，聊天上下文只使用该描述
- 允许从输入区发起图片生成；生成结果必须成为普通图片消息，因此自动拥有“加入相册 / 收录至作品”等既有对象操作
- 图片上传继续遵守相册的 MIME / 大小边界；视觉或生成失败必须保留用户原图并给出失败反馈

### 9.6.2 富消息块

- `html` 只能在无权限 iframe 中展示，并用 CSP 禁止脚本、表单、导航与网络请求；禁止 `dangerouslySetInnerHTML`
- `widget` 只展示协议声明的标题与来源，不执行任意脚本
- `tab-group` 只允许一层叶子块；不为视觉方便引入递归块或升级 Dexie

## 9.7 MCP 工具

聊天页提供 Mini Terminal，作为 MCP 工具的**用户可见、用户发起**出口：

- 工具清单来自现有 ToolGateway；没有可用 MCP Server 时显示空态与诊断提示，不伪造演示工具
- 用户先选择 Server 与工具、查看参数 schema，再填写参数；点击“确认调用”即本次显式授权
- 每次结果都写成当前会话的一条 `tool-result` 消息：成功 / 失败、工具名、摘要与原始结果均可追溯
- 邮件等高风险能力不建立旁路：若 MCP 中存在对应工具，同样从 Mini Terminal 显式发起并留下结果记录
- 参数不是合法 JSON、Server 未就绪、调用失败都在面板内显示；失败不能静默，也不能伪造成成功消息
- Mini Terminal 展示工具事件与结果，不展示隐藏 system prompt、模型思维链或服务端密钥
- AI 自主工具调用**已启用**（Phase 6.5）：允不允许由能力的**自主级别**决定，不由工具自身决定 ——
  `autonomous` 直接执行、`confirm` 必须先挂起等你点「允许」、`unavailable` 的工具**根本不会绑给模型**。
  服务端不接受模型绕过分级直接执行；每次调用都在会话里留下工具卡片，写类操作另留一条事件记录
- 自主调用的结果与 Mini Terminal 的结果用**同一套呈现**（`tool-result` 消息），不因为「谁发起的」而分叉

## 9.8 应用外壳与导航

外壳是所有页面共用的那一层：底部导航、欢迎页、子页面怎么进出。它只管**在栖息地里怎么走动**，
不承载任何业务内容 —— 换外壳不该改变任何一条数据或接口。

### 9.8.1 底部导航

- 五个入口，顺序固定：**对话 / 家 / 大脑 / 生活 / 设置**，分别指向 `/chat`、`/home`、`/llm`、`/life`、`/setting`
- 形态是**浮起的胶囊**：不贴边、半透明毛玻璃、圆角、轻投影。内容在其**下方**滚动而不是被顶开；
  底部避让用实测出的高度令牌，不写魔法数字
- 图标是**线框**；当前所在的那一项**变成实心**来表达「你在这里」—— 靠形状而不是颜色，
  这样选中态在深浅两套配色里都成立
- 名称用中文。**「大脑」= `/llm`**，即小栖能力档案；换模型**不在这里**，在设置页（§9.3）
- 会话窗口（`/chat/:sessionId`）是沉浸式的，**不显示底部导航**（§2.2）
- 底部导航必须是**真链接**（`<a href>`）：新标签页打开、长按复制链接等浏览器原生行为要照常可用

### 9.8.2 欢迎页

- 打开栖息地先看到欢迎页：雨幕背景、当前时间与问候、小栖的最近消息叠卡、「进入栖息地」
- 它**不是每次刷新都出现**：一次「新会话」（冷启动）内只出现一次，进入后本次会话不再拦截；
  想再看到可以直接访问 `/welcome`。**不做**每次打开都强制看一眼的门槛
- 点叠卡或「进入栖息地」都进入 `/chat`（对话是主线，`/` 也照旧落到对话）
- 叠卡展示的是**最近一条来自小栖的消息**（正文 + 相对时间），数据取自真实会话；
  **没有消息就换成安静的空态引导**，不编造「2 条未读」这类数字
- 欢迎页不显示底部导航

### 9.8.3 子页面进出

- Home 的子页面（日记 / 收藏 / 作品 / 相册 / 音乐 / 学习……）**保留各自的真实网址**（如 `/home/diary`）：
  刷新、后退、加书签、分享链接都必须照常工作
- 「滑进来」是**动画**，不是换屏机制：子页面从右侧滑入覆盖，页内左上角提供返回
- ⚠️ **不采用**原型里「所有页面绝对定位叠放、靠 class 切显示」的做法 ——
  那会让刷新与后退失效，也会让深链（直接打开某个子页面）变成白屏
- 从 URL 直接进入子页面时视作直接打开，不播放进入动画

# 10. 后续施工流程建议

每开发或重构一个模块前：

1. 先读取本文件对应章节
2. 明确用户 / AI 权限
3. 明确主流程与对象操作
4. 明确跨模块联动
5. 再决定数据与技术实现
6. 做最小可用实现
7. 本地验房
8. 记录 UX 偏差
9. 修正后再进入下一阶段

# 11. v0.1 结论

本版先完成两件事：

1. **把 Chat 从“能聊天”提升为“能长期使用的消息空间”**
2. **把 Home 从“一组独立 CRUD 页面”重新定义为“共同生活 + 跨模块内容汇聚层”**

后续开发应优先遵循真实使用路径，避免只以“功能能保存、能展示”为完成标准。
